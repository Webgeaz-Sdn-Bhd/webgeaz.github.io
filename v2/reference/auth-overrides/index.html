    Authentication page transactions¶

    Applications using local authentication can customize every built-in auth page with a transaction in the reserved auth group. The framework still handles credential checks, account changes, sessions, CSRF, permissions, and redirects. The transaction supplies the page and, for auth/login, optional login hooks. This convention activates when the auth mode is local and the security profile is authenticated or mixed. It does not apply to public or custom-provider applications.

    Screen codes and files¶

    Built-in screen Transaction code
    Sign in login
    Two-factor verification verify_totp
    Registration register
    First administrator bootstrap
    Forgot password forgot
    Reset password reset
    Invitation invite
    Profile profile
    Sessions sessions
    Authenticator setup totp_setup
    User administration admin_users
    Authentication error error

    Use the normal transaction files. For example, the IDE's auth/login transaction contains auth/login.py with class Login, plus its default view at auth/_login/login.html. The runtime path is webapp/WEB-INF/jython/default/auth/. Create and edit these files through the IDE transaction editor or its normal AI transaction tools.

    class Login(object):
    def view(self, ctx):
        ctx.output["welcome_text"] = "Welcome back"

    The framework calls view(ctx) before rendering the default Handlebars view. It passes the built-in page data in ctx.output, including title, message, error, csrf_token, context_path, ctxPath, action_url, and the page's navigation URLs and account data. Use {{action_url}} for the built-in form and {{csrf_token}} in its hidden input. These pages are full HTML documents; the application layout is not applied. A callable alternate view assigned to ctx.go_to is allowed, but redirects and direct response writes are not.

    These transactions are invoked only at /_soad/auth/*. In local mode, direct /t/auth/<screen-code> requests return 404. Do not add ACCESS_POLICY or implement a second form POST action. If the transaction is absent or its page fails to render or validate, the framework serves its built-in page.

    Login hooks¶

    auth/login may define two optional methods:

    class Login(object):
    def view(self, ctx):
        pass

    def before_login(self, ctx):
        # Runs after CSRF and rate-limit checks, before password verification.
        ctx.getRequest().getSession(True).setAttribute("login_source", "web")

    def after_login(self, ctx, user):
        # Runs once after a successful local session is established.
        ctx.getRequest().getSession(True).setAttribute(
            "signed_in_email", user["email"])

    after_login runs for password sign-in, completion of two-factor sign-in, registration, first-administrator bootstrap, and sign-ins through auth.admin. user contains public identity fields (id, email, login_id, and full_name), never a password or TOTP secret. Hooks may update the session but cannot redirect or write the response. A hook failure stops sign-in; if a session was just created, the framework revokes and clears it. Account creation already committed by registration or bootstrap remains created.

    Page safety and assets¶

    The framework checks view source and rendered HTML. Every form screen must keep its built-in form action and required input names, with the actual CSRF token in a csrf_token input. Unescaped Handlebars values ({{{...}}} and {{&...}}), frames/objects, executable URLs, off-origin links or resources, <base>, and refresh redirects are refused. Pre-sign-in screens also refuse scripts and inline event handlers. The signed-in profile, sessions, totp_setup, and admin_users screens may use inline scripts, but not remote or module scripts. An invalid page is logged and replaced by the built-in page.

    The optional stylesheet remains at webapp/assets/auth-overrides/auth.css. Built-in pages link it automatically, so a CSS-only customization needs no auth transaction. An auth transaction view may link {{stylesheet_url}} itself. The optional self-contained logo stays at webapp/WEB-INF/auth-overrides/mark.svg; it appears only on built-in pages. Both assets can be staged with the AI stage_auth_override tool using stylesheet or mark.
