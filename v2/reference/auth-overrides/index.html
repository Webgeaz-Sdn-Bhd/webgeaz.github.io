    Authentication override contract¶

    Everything required to produce a drop-in replacement for the built-in authentication UI. A generator that follows this document can emit a folder that is copied into a deployed application and works without a restart.

    This document is structure only — it defines filenames, required markup, available data, and the validator rules. All visual design (layout, palette, typography, spacing, component styling) is left to the generator.

    Source of truth: app/server/auth/overrides.py (validator) and app/server/AuthServlet.py (context builder). See also application security.

    1. Output layout¶

    ⚠️ Not every file goes into WEB-INF/auth-overrides/. The stylesheet must be web-reachable, so it lives under webapp/assets/. Emitting auth.css into WEB-INF/auth-overrides/ results in a silently unstyled page — the file is never read and never served.

    Generate this tree, rooted at the application's webapp/ directory:

    webapp/
├── WEB-INF/
│   └── auth-overrides/
│       ├── login.html
│       ├── verify-totp.html
│       ├── register.html
│       ├── bootstrap.html
│       ├── forgot.html
│       ├── reset.html
│       ├── invite.html
│       ├── profile.html
│       ├── sessions.html
│       ├── totp-setup.html
│       ├── admin-users.html
│       ├── error.html
│       └── mark.svg          (optional logo; NOT a template — see §8)
└── assets/
    └── auth-overrides/
        └── auth.css          (optional stylesheet — MUST be here, not WEB-INF)

    Rules:

    • Every file is independently optional. A screen with no override file falls back to the framework page. A partial set is valid.
    • No other filenames are recognized. Extra files in the folder are ignored — there is no way to add a page, a second stylesheet, an image, or a font file. Everything a page needs must be in its own .html or in auth.css.
    • Files are read per request, not cached. Adding, editing, or deleting a file takes effect on the next page load. No restart, no rebuild. (Contrast with ActiveJDBC models, which do require a restart.)
    • UTF-8 only. Files are read as UTF-8; any other encoding makes the screen fall back.
    • Deleting a file restores the framework default.
    • Overrides apply only when the application's auth mode is local. public mode has no login UI; a custom provider owns its own flow.

    Size limits (exceeding = rejected):

    File Limit
    any .html 128 KiB
    auth.css 256 KiB
    mark.svg 24 KiB

    2. Failure behavior — what "no error upon run" means¶

    An invalid override never produces a 500 or a broken page. The framework:

    1. calls the validator on every render (not just at install time),
    2. on any failure, logs WARNING: Invalid authentication override <screen>,
    3. renders its own built-in page instead.

    So the failure mode is silent reversion to the default look. If a generated page "does nothing", the file is being rejected — check the server log for the warning, which names the screen and the exact reason.

    Because validation runs per request, keep pages lean; multi-hundred-KiB pages pay a regex + Handlebars compile on every hit.

    3. Hard rules — any one of these rejects the file¶

    The screens fall into two groups, and the script rules differ between them:

    • Pre-sign-in screens — login, verify-totp, register, bootstrap, forgot, reset, invite, error. Shown to an anonymous visitor, carrying the password field and the CSRF token. No JavaScript of any kind.
    • Signed-in management screens — profile, sessions, totp-setup, admin-users. Reached only after authentication (admin-users additionally requires the auth.users.manage permission). Inline JavaScript is allowed.

    Rejected on every screen:

    Rejected Use instead
    <script src="…"> — any external script, incl. a CDN tag inline <script> on a management screen; auth.css for styling
    <script type="module"> — its import can fetch remote code with no src a classic inline <script>
    <iframe>, <frame>, <frameset>, <object>, <embed>, <applet> plain HTML elements
    href/xlink:href/src/action/formaction starting javascript:, vbscript:, data:text/html a normal path
    The same attributes starting https://, http://, or //host — a CDN stylesheet, a remote image, a font host, an off-site form target, an outbound <a> a path on this application; embed an image or font as a data: URI
    <base> — it silently re-points every relative URL, including the form carrying the password nothing; the URLs you need are in the page context
    <meta http-equiv="refresh"> let the server redirect
    {{{value}}} or {{&value}} (unescaped output) {{value}} — always escaped

    A data: URI of an image or font type is fine, and so are mailto: and tel: — none of them fetches from another origin. {{stylesheet_url}}, {{context_path}}/…, #fragment, and any relative path are unaffected.

    Rejected on the pre-sign-in screens only:

    Rejected Use instead
    <script> in any form, including inline auth.css — it is linked into every page
    Inline event handlers — any attribute matching on…= (onclick, onsubmit, onload, …) nothing; the forms are plain HTML POSTs and work without JS

    auth.css: no expression(, javascript:, vbscript:, url(data:text/html…), and no @import or url() pointing at another origin.

    Three implementation details that trip generators:

    • The check runs on HTML-unescaped text. Writing &lt;script&gt; as visible page text still trips the script rule. Do not put these constructs in prose.
    • On a pre-sign-in screen the event-handler pattern is on<word>=, matched anywhere, including in text content. A sentence such as run once = twice matches and rejects the file. Avoid a word beginning with "on" followed directly by =. (This trap does not apply to the four management screens.)
    • Attribute values must be quoted. The required-input check matches name="email" or name='email'; unquoted name=email fails.

    On the pre-sign-in screens, no JavaScript at all is the single biggest constraint. Every interaction must be a plain form submit or a link. Client-side validation, password-strength meters, show/hide-password toggles, and AJAX are impossible there. CSS-only interaction (:focus-within, :checked, :has()) is permitted and is the supported way to get interactive behavior.

    On the four management screens, write the script inline in the page — a modal, a disclosure panel, a confirm-before-revoke, a client-side filter over the user list are all fine. Those routes also send a Content-Security-Policy (script-src 'self' 'unsafe-inline', connect-src 'self', object-src 'none', frame-ancestors 'none', img-src 'self' data:), so a remote import() or a fetch() to a third-party origin is blocked by the browser even though no regex inspects the script body. Keep the page working if the script does not run: these are the screens a user manages their own credentials from.

    4. Page shell — required, and easy to get wrong¶

    An HTML override replaces the entire document. The framework's layout is not applied around it. Consequences the generator must handle:

    • It must emit a complete document: <!doctype html>, <html>, <head>, <body>. Nothing is added.
    • No stylesheet is linked for you. Emit the links yourself.
    • mark.svg is not injected into an overridden page. The logo override only applies to screens still using the framework page. An override that wants a logo must inline its own SVG (subject to §3's rules) or draw it in CSS.
    • {{message}} and {{error}} are not rendered for you. If the page does not output them, the user never sees "Invitation accepted", "Too many attempts", or "Passwords do not match". Render both on every screen.

    Two stylesheet URLs are in the context of every screen:

    Variable Points at Use
    {{default_stylesheet_url}} the framework's auth.css link it first to inherit framework styling, or omit it entirely to start from a blank slate
    {{stylesheet_url}} your webapp/assets/auth-overrides/auth.css link it last

    Required shell (structure only — design is the generator's):

    <!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width,initial-scale=1">
<meta name="robots" content="noindex,nofollow">
<title>{{title}}</title>
<link rel="stylesheet" href="{{stylesheet_url}}">
</head>
<body>
  {{#if error}}<div class="notice error">{{error}}</div>{{/if}}
  {{#if message}}<div class="notice success">{{message}}</div>{{/if}}
  <!-- screen body, per §6 -->
</body>
</html>

    noindex,nofollow is on the framework pages and should be kept.

    If auth.css is not generated, drop the {{stylesheet_url}} link — otherwise every page load logs a 404 for a file that does not exist.

    5. Template language — the available subset¶

    Handlebars (Java, jknack). Available helpers and nothing else:

    • Built-ins: if, unless, each, with, lookup, log
    • Comparison: eq, neq, gt, gte, lt, lte, and, or, not

    The app-view helpers from server/utils/render.py — select, option, ref_lookup, dateFmt, in, html, session, i18n, get — are deliberately unavailable here. Using one is a compile failure, and the screen falls back.

    {{#if registration_open}}<a href="{{register_url}}">Create an account</a>{{/if}}
{{#each users}}<li>{{full_name}} — {{email}}</li>{{/each}}
{{#if (eq status "active")}}…{{/if}}

    All output is HTML-escaped. There is no way to emit raw HTML from a value.

    6. Per-screen contract¶

    Common context — present on every screen¶

    Variable Type Notes
    title string the framework's title for the screen
    message string success notice; "" when none
    error string error notice; "" when none
    csrf_token string see below
    context_path string servlet context path; "" at root
    default_stylesheet_url string framework auth.css
    stylesheet_url string your auth.css

    The two structural requirements¶

    For every screen that has inputs (all except error):

    1. A <form> with an action attribute must appear in the file. Matched as <form … action=…> within one tag.
    2. Every listed input name must appear as name="…", and the literal {{csrf_token}} placeholder must be present. A hardcoded hidden field does not satisfy this — the placeholder is required precisely so that CSRF protection cannot be disabled by a template.

    Standard CSRF field for every form:

    <input type="hidden" name="csrf_token" value="{{csrf_token}}">

    The check is a regex over the raw file, so names inside {{#if}} / {{#each}} blocks count as present even if that branch never renders. A screen with two mutually exclusive forms (totp-setup) satisfies the check by containing both.

    login.html — POST {{action_url}}¶

    Required names: email, password, csrf_token

    Variable Type Notes
    action_url string POST target
    forgot_url string password recovery
    register_url string only meaningful when registration_open
    registration_open bool show/hide the register link
    bootstrap_available bool true when no administrator exists yet; link to {{context_path}}/_soad/auth/bootstrap 
    <form method="post" action="{{action_url}}">
  <input type="hidden" name="csrf_token" value="{{csrf_token}}">
  <input type="email" name="email" required>
  <input type="password" name="password" required>
  <button type="submit">Sign in</button>
</form>
<a href="{{forgot_url}}">Forgot password?</a>
{{#if registration_open}}<a href="{{register_url}}">Create an account</a>{{/if}}
{{#if bootstrap_available}}
  <a href="{{context_path}}/_soad/auth/bootstrap">Set up the first administrator</a>
{{/if}}

    verify-totp.html — POST {{action_url}}¶

    Shown after a correct password when TOTP is enabled. Credentials are already held in the session; the form carries only the code.

    Required names: code, csrf_token Context: action_url

    register.html — POST {{action_url}}¶

    Only reachable when open registration is enabled.

    Required names: full_name, email, password, password_confirm, csrf_token Context: action_url, login_url

    bootstrap.html — POST {{action_url}}¶

    First-administrator setup; reachable only while no active administrator exists.

    Required names: full_name, email, password, password_confirm, csrf_token Context: action_url, login_url, password_min_length (integer, currently 10)

    Use minlength="{{password_min_length}}" on both password inputs.

    forgot.html — POST {{action_url}}¶

    One template serves both the empty form and the post-submit confirmation; branch on submitted.

    Required names: email, csrf_token Context: action_url, login_url, submitted (bool)

    The response is deliberately generic — it does not reveal whether the account exists. Do not word the confirmation as though it does.

    reset.html — POST {{action_url}}¶

    Required names: token, password, password_confirm, csrf_token Context: action_url, token, login_url, password_min_length

    token must be carried through as a hidden field:

    <input type="hidden" name="token" value="{{token}}">

    invite.html — POST {{action_url}}¶

    Invitation acceptance / initial password. Identical shape to reset.html; a separate file so the wording can differ.

    Required names: token, password, password_confirm, csrf_token Context: action_url, token, login_url, password_min_length

    The four screens that follow — profile, sessions, totp-setup, admin-users — are the signed-in management screens. They are the only ones that accept an inline <script> and inline event handlers (see §3), and the only ones that get the wide card. error, after them, is back to the pre-sign-in rules.

    Shared shell context — on all four, so the same nav, sign-out link, and "signed in as" can be pasted into each:

    Variable Type Notes
    profile_url, sessions_url, totp_setup_url, admin_users_url string navigation
    logout_url string plain link; the CSRF token is already in the query string, so a template cannot build this itself
    user object id, email, full_name, status

    {{admin_users_url}} is present for every user; non-administrators get 403 on that page. Hide it or accept the 403 — there is no "is admin" flag here.

    profile.html — two forms¶

    Required names: full_name, current_password, password, password_confirm, csrf_token

    Variable Type Notes
    action_url string POST — profile update (full_name)
    password_action_url string POST — password change

    Two separate forms are required — one to {{action_url}} with full_name, one to {{password_action_url}} with current_password + password + password_confirm. Each needs its own CSRF field.

    sessions.html — POST {{revoke_action_url}} per row¶

    Required names: session_id, csrf_token

    Variable Type Notes
    revoke_action_url string POST target
    sessions array see below

    Each entry of sessions: id, created_at, last_seen_at, user_agent, ip_address — all strings, pre-defaulted ("Unknown client", "unknown address"), newest first.

    Each row needs its own form; there is no bulk revoke endpoint.

    {{#each sessions}}
  <li>
    {{user_agent}} — {{ip_address}} — {{last_seen_at}}
    <form method="post" action="{{../revoke_action_url}}">
      <input type="hidden" name="csrf_token" value="{{../csrf_token}}">
      <input type="hidden" name="session_id" value="{{id}}">
      <button type="submit">Revoke</button>
    </form>
  </li>
{{/each}}

    Note the ../ prefix inside {{#each}}. The validator's {{csrf_token}} check is satisfied by the shell's plain {{csrf_token}}, but each form still needs the ../-qualified value to actually render — so include at least one bare {{csrf_token}} outside the loop if every form is inside one.

    totp-setup.html — two mutually exclusive states¶

    Required names: code, current_password, csrf_token — all three must be in the file even though only one state renders at a time.

    Variable Type Notes
    enabled bool branch on this
    secret string base32 secret; "" when already enabled
    qr_data_url string data:image/… for <img src="…">; "" when enabled
    setup_action_url string POST — enable (field code)
    disable_action_url string POST — disable (field current_password)

    {{qr_data_url}} in an src attribute is allowed — only data:text/html is blocked, image data URLs are fine. Show {{secret}} as text too, for users who cannot scan.

    {{#if enabled}}
  <form method="post" action="{{disable_action_url}}">
    <input type="hidden" name="csrf_token" value="{{csrf_token}}">
    <input type="password" name="current_password" required>
    <button type="submit">Disable</button>
  </form>
{{else}}
  <img alt="TOTP QR code" src="{{qr_data_url}}">
  <code>{{secret}}</code>
  <form method="post" action="{{setup_action_url}}">
    <input type="hidden" name="csrf_token" value="{{csrf_token}}">
    <input name="code" inputmode="numeric" required>
    <button type="submit">Enable</button>
  </form>
{{/if}}

    admin-users.html — four POST targets¶

    The most demanding screen. Required names: email, user_id, role_code, operation, status, csrf_token — all six, even for a minimal page.

    Variable Type Notes
    create_action_url string POST — add user
    invite_action_url string POST — (re-)send setup link; field email
    role_action_url string POST — grant/remove role
    status_action_url string POST — enable/disable
    users array see below
    roles array { code, name }
    form object re-populates the add-user form after a validation error: full_name, email, role_codes (array)
    invite_link string one-time setup link, "" when none
    invitation_created bool true only on the invite-result render, where users and roles are empty

    Each entry of users: id, email, full_name, status, pending (bool), roles (array of role-code strings), next_status (the value to post to flip enabled/disabled).

    pending means the account exists but has no password — it cannot sign in until the setup link is followed. Render it distinctly from active.

    The four operations:

    {{! 1. add user — role_codes is a repeated checkbox, name is PLURAL here }}
<form method="post" action="{{create_action_url}}">
  <input type="hidden" name="csrf_token" value="{{csrf_token}}">
  <input name="full_name" value="{{form.full_name}}" required>
  <input type="email" name="email" value="{{form.email}}" required>
  {{#each roles}}
    <label><input type="checkbox" name="role_codes" value="{{code}}"> {{name}}</label>
  {{/each}}
  <input type="password" name="password" minlength="10">
  <input type="password" name="password_confirm" minlength="10">
  <button type="submit">Create user</button>
</form>
{{! leaving both password fields empty creates a pending account + setup link }}

{{#if invite_link}}<p><a href="{{invite_link}}">{{invite_link}}</a></p>{{/if}}

{{#each users}}
  <li>
    {{full_name}} — {{email}} — {{#if pending}}pending{{else}}{{status}}{{/if}}
    {{#each roles}}<span>{{this}}</span>{{/each}}

    {{! 2. grant/remove a role — role_code is SINGULAR here }}
    <form method="post" action="{{../role_action_url}}">
      <input type="hidden" name="csrf_token" value="{{../csrf_token}}">
      <input type="hidden" name="user_id" value="{{id}}">
      <input type="hidden" name="operation" value="grant">
      <select name="role_code">
        {{#each ../roles}}<option value="{{code}}">{{name}}</option>{{/each}}
      </select>
      <button type="submit">Grant</button>
    </form>

    {{! 3. enable/disable }}
    <form method="post" action="{{../status_action_url}}">
      <input type="hidden" name="csrf_token" value="{{../csrf_token}}">
      <input type="hidden" name="user_id" value="{{id}}">
      <input type="hidden" name="status" value="{{next_status}}">
      <button type="submit">{{#if (eq status "active")}}Disable{{else}}Enable{{/if}}</button>
    </form>

    {{! 4. re-send setup link — only useful for pending accounts }}
    {{#if pending}}
    <form method="post" action="{{../invite_action_url}}">
      <input type="hidden" name="csrf_token" value="{{../csrf_token}}">
      <input type="hidden" name="email" value="{{email}}">
      <button type="submit">Re-send setup link</button>
    </form>
    {{/if}}
  </li>
{{/each}}

    Watch the two role field names: role_codes (plural, checkboxes, create form) and role_code (singular, select, grant/remove). Only the singular one is required by the validator; the plural create-form fields are optional — a template that omits them keeps validating and simply does not offer that feature. To remove a role, post operation = remove instead of grant.

    {{invite_link}} must be shown when non-empty: with SMTP unconfigured it is the only way the administrator can deliver the setup link.

    error.html — no form¶

    Used for every failure response: 400, 403 (CSRF mismatch, non-admin), 404 (disabled feature, unknown page), 500, 503 (schema/manifest not ready).

    Required names: none. No form or CSRF needed.

    Variable Type Notes
    status integer HTTP status
    error string the message; also in {{error}}

    The HTTP status code is preserved regardless of what the template renders. Keep the message generic — it is shown to unauthenticated visitors.

    7. auth.css¶

    Path: webapp/assets/auth-overrides/auth.css, served at {{stylesheet_url}} (= <context>/assets/auth-overrides/auth.css).

    • Rejected: expression(, javascript:, vbscript:, url(data:text/html…), and any @import or url() pointing at another origin (https://, http://, //host).
    • Limit 256 KiB.
    • Self-contained. There is no second file, no image, no font file — the folder recognizes only the names in §1. Embed any image or font as a data: URI (image/font types are fine; only data:text/html is blocked). Do not @import or reference a CDN: these pages are built for air-gapped deployments, and a fetch that fails leaves the login screen unstyled.
    • If the generator emits full-page HTML overrides with self-contained class names, it does not need to link {{default_stylesheet_url}}, and the framework class names below are irrelevant.
    • If the generator overrides only some screens, the non-overridden ones still render with the framework layout, which links the framework stylesheet and then yours. In that case auth.css is a cascade layer over the defaults, and these are the framework's hooks:

    .auth-card / .auth-card.wide, .auth-mark, .auth-body, .notice, .notice.error, .notice.success, nav.tab-bar, .row-main, .row-identity, .row-sub, .row-roles, .row-actions, .badge, .badge-active, .badge-disabled, .badge-pending, .chip, .chip-remove, .inline, .form-hint, .link-box, .role-picker, .role-option.

    .wide is applied to profile, sessions, totp-setup, and admin-users; the other screens are the narrow centered card.

    Recommended: for a consistent result, generate either all 12 HTML files, or none of them plus auth.css only. A partial HTML set means overridden and framework screens sit side by side in the same flow.

    8. mark.svg (optional logo)¶

    Path: webapp/WEB-INF/auth-overrides/mark.svg.

    This only affects screens rendered by the framework layout. An overridden HTML page does not receive it — inline the logo in that page's own markup instead. It is worth generating only when shipping auth.css without HTML overrides.

    Not a Handlebars template — inlined verbatim. Its rules:

    • The whole file is one <svg>…</svg> element. No <?xml?>, no <!DOCTYPE>, no <!ENTITY>, nothing before or after the root tag.
    • No <script>, no on…= handlers, no <iframe>/<object>/<embed>/ <foreignObject>.
    • href/xlink:href may only be a local #fragment (e.g. <use> referencing a <symbol> in the same file). No external file, no data: URL.
    • Build from shape elements: <svg>, <g>, <path>, <circle>, <ellipse>, <rect>, <polygon>, <use>.
    • 24 KiB limit.
    • Set a viewBox; omit width/height. Any class or aria-hidden on the root is stripped and replaced with class="auth-mark" aria-hidden="true", so sizing comes from CSS.
    • Shown on the narrow screens only (login, register, forgot, reset, invite, verify-2FA, error). Wide management screens never show it.

    9. Generator checklist¶

    Per HTML file:

    • [ ] Complete document: doctype, <html>, <head>, <body>
    • [ ] <title>{{title}}</title> and the {{stylesheet_url}} link (only if auth.css is generated)
    • [ ] Both {{message}} and {{error}} rendered
    • [ ] Every required input name from §6, quoted: name="email"
    • [ ] A literal {{csrf_token}} placeholder, plus a CSRF hidden field in every form (../csrf_token inside {{#each}})
    • [ ] Every form has an action attribute pointing at the screen's *_action_url
    • [ ] No {{{…}}}, and no <script src=…> or <script type="module"> anywhere
    • [ ] On a pre-sign-in screen: no <script> at all and no on…= attribute (check prose text too). On profile / sessions / totp-setup / admin-users: inline script and handlers are fine
    • [ ] Only the §5 helpers used
    • [ ] Under 128 KiB, UTF-8

    Per output set:

    • [ ] auth.css at webapp/assets/auth-overrides/, not WEB-INF/
    • [ ] No files other than the names in §1
    • [ ] No external URL anywhere — no CDN, font host, or remote image. This is enforced, not advisory: an https://, http://, or //host URL in href/src/action/formaction, or in a CSS @import/url(), rejects the file

    10. Scope¶

    An override changes presentation only. It cannot change credential verification, session handling, CSRF, roles, permissions, rate limiting, or token lifetimes, and it cannot add or remove a route. For different authentication behavior, use a custom provider instead.
