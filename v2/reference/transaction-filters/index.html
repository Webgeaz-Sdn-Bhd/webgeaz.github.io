    Transaction filter reference¶

    Transaction filters let an application run reusable request and response logic around the normal servlet pipeline. They are useful for concerns such as request logging, response headers, maintenance gates, correlation IDs, and other logic that must run before or after a request reaches a servlet.

    SØAD implements this feature with one framework filter mapped to /*. The framework filter discovers transaction classes in the reserved filter group and presents each one as a servlet-style filter.

    Quick start¶

    Create a transaction named filter/request_logger:

    webapp/WEB-INF/jython/default/
├── __init__.py
└── filter/
    ├── __init__.py
    └── request_logger.py

    Define all three lifecycle methods in request_logger.py:

    from java.util.logging import Level, Logger


logger = Logger.getLogger("filter.request_logger")


class Request_logger(object):
    url_mapping = "/*"

    def filter_init(self, config):
        logger.log(Level.INFO, "Request logger initialized")

    def do_filter(self, request, response, chain):
        logger.log(Level.INFO, "Request: %s" % request.getRequestURI())
        chain.doFilter(request, response)

    def destroy(self):
        logger.log(Level.INFO, "Request logger destroyed")

    Restart or redeploy the server after creating, deleting, renaming, or changing a transaction filter. Discovery and transaction instances are cached for the lifetime of the framework filter.

    Required contract¶

    A Python file qualifies as a transaction filter when all of the following are true:

    • It is directly under webapp/WEB-INF/jython/default/filter/.
    • Its filename is a valid transaction code, for example request_logger.py.
    • It declares the conventional transaction class. The filename request_logger.py maps to the class Request_logger.
    • The class implements filter_init, do_filter, and destroy with the signatures described below.
    class Example(object):
    url_mapping = "/*"

    def filter_init(self, config):
        pass

    def do_filter(self, request, response, chain):
        chain.doFilter(request, response)

    def destroy(self):
        pass

    The filter group is reserved for this contract. A filter transaction is not a normal MVC endpoint: do not add view(ctx), a Handlebars view directory, or an ACCESS_POLICY merely to make it look like a routed transaction.

    filter_init(config)¶

    The framework calls filter_init once after constructing the filter. config is the jakarta.servlet.FilterConfig of the framework dispatcher and provides access to the servlet context and configured initialization parameters.

    Use this method for immutable setup that can be shared safely across requests. If it raises an exception, filter initialization fails and the error is allowed to propagate to the servlet container.

    do_filter(request, response, chain)¶

    The framework calls do_filter for every request that matches the transaction's URL mapping. The arguments are the current servlet request, servlet response, and continuation chain.

    Call chain.doFilter(request, response) exactly once to continue to the next matching transaction filter and eventually the requested servlet. Code before that call is pre-processing; code after it is post-processing:

    class Timing(object):
    def filter_init(self, config):
        pass

    def do_filter(self, request, response, chain):
        started = System.nanoTime()
        try:
            chain.doFilter(request, response)
        finally:
            elapsed = System.nanoTime() - started
            # Record elapsed here.

    def destroy(self):
        pass

    Import System from java.lang when using the timing example.

    A filter may intentionally omit the chain call to short-circuit the request. When it does, it must complete the response itself:

    class Maintenance(object):
    url_mapping = "/t/admin/*"

    def filter_init(self, config):
        pass

    def do_filter(self, request, response, chain):
        if request.getHeader("X-Maintenance-Bypass") is None:
            response.sendError(503, "Service temporarily unavailable")
            return
        chain.doFilter(request, response)

    def destroy(self):
        pass

    Do not catch and suppress downstream errors unless the filter has a documented recovery policy. An exception raised by a transaction filter, a later filter, or the target servlet propagates with normal servlet-filter behavior.

    destroy()¶

    The framework calls destroy during shutdown or filter replacement. Release resources created by filter_init here. Filters are destroyed in reverse initialization order. Destruction failures are not silently converted into successful shutdowns.

    URL mappings¶

    Declare an optional class-level url_mapping. It may be one string or a list of strings. When it is absent, the mapping defaults to /*.

    class Api_headers(object):
    url_mapping = ["/t/api/*", "*.json"]

    def filter_init(self, config):
        pass

    def do_filter(self, request, response, chain):
        response.setHeader("X-Content-Type-Options", "nosniff")
        chain.doFilter(request, response)

    def destroy(self):
        pass

    Mappings follow servlet URL-pattern conventions:

    Pattern Matches
    /* Every request
    /health Only the exact /health path
    /t/api/* /t/api and paths below it
    *.json Any request path ending in .json

    Patterns are matched against the request path relative to the servlet context. The query string is not part of the match. A list matches when any one of its patterns matches. An empty value, unsupported pattern, or non-string list item is a configuration error and fails initialization.

    The transaction mapping decides whether that transaction is invoked; it does not register another container filter. The single framework dispatcher remains mapped to /*.

    Discovery, order, and application scope¶

    The dispatcher scans only the default/filter package. These filters are deployment-wide and may therefore see requests for named applications, built-in authentication routes, static resources, and other servlets. Always narrow url_mapping when a filter should affect only part of the server.

    Eligible filters are initialized and invoked in ascending alphabetical order by transaction code. For deliberate ordering, use descriptive prefixes that still follow transaction naming rules:

    filter/a_request_id.py
filter/b_request_log.py
filter/c_response_headers.py

    Only filters whose mapping matches the current request enter that request's chain. Post-processing runs in the reverse order naturally as nested chain calls return.

    Discovery happens during dispatcher initialization and is cached. A server restart or redeployment is required after adding, removing, or renaming a filter and after changing filter code or mappings.

    Failure handling¶

    The filter group is tolerant of incomplete transaction files but strict once a filter qualifies:

    Condition Behavior
    One or more required lifecycle methods are missing Skip the transaction and log a warning
    Module import or class construction fails Fail initialization and propagate the error
    url_mapping is invalid Fail initialization and propagate the error
    filter_init fails Fail initialization and propagate the error
    do_filter or downstream processing fails Propagate the request error
    destroy fails Report the destruction error

    Skipping an incomplete class supports ordinary files being inspected while they are being created, but it can also hide an intended security filter. Check the server log after deployment and test security-sensitive filters explicitly.

    Runtime and concurrency rules¶

    Transaction filter instances follow servlet-filter singleton semantics. One cached instance may serve many requests concurrently.

    • Do not store request-specific data on self.
    • Prefer local variables and request attributes for per-request state.
    • Make shared mutable state thread-safe.
    • Keep filter_init setup immutable where possible.
    • Do not assume a WebContext, ActiveJDBC connection, or database transaction.
    • Do not assume the request is a /t/... transaction request.
    • Do not write a response after it has been committed by downstream processing.

    The arguments to do_filter are raw servlet objects. If a filter needs a value later in the request pipeline, attach it to the request:

    request.setAttribute("correlation_id", correlation_id)

    Default framework registration¶

    The framework dispatcher is enabled in both development and production runtime profiles with:

    filter.transaction_filter.mapping = /*
filter.transaction_filter.file = server/TransactionFilter.py

    Applications normally do not need to add these properties themselves. If a custom runtime configuration replaces the supplied sufia.properties, retain both entries to keep transaction-filter support enabled.

    AI agent generation rules¶

    When an AI agent creates or edits a transaction in the filter group, it must apply the following rules:

    1. Treat filter as the reserved deployment-wide transaction-filter group.
    2. Generate one controller file and no view templates unless the developer explicitly requests unrelated files.
    3. Generate the conventional capitalized class with all three methods: filter_init(config), do_filter(request, response, chain), and destroy().
    4. Do not generate view(ctx) or ACCESS_POLICY for the filter contract.
    5. Declare url_mapping only when needed; otherwise rely on the /* default.
    6. Call chain.doFilter(request, response) exactly once for normal continuation, or intentionally complete the response and return for a short circuit.
    7. Preserve servlet exception behavior; do not add a blanket exception handler that hides failures.
    8. Keep the instance thread-safe and do not place request state on self.
    9. Tell the developer that a restart or redeployment is required for the change to be discovered.

    Before proposing a filter, the agent should state its transaction code, URL mapping, whether it continues or short-circuits the chain, and any shared state created during initialization.

    Review checklist¶

    • The file is under default/filter and its class name matches its filename.
    • All three lifecycle methods use the exact required signatures.
    • The mapping is absent, a valid string, or a valid list of strings.
    • The chain is called exactly once on every continuation path.
    • Every short-circuit path completes the response.
    • Exceptions are allowed to propagate unless recovery is intentional.
    • Shared state is safe for concurrent requests.
    • The mapping is narrow enough for deployment-wide scope.
    • Deployment includes a server restart or redeployment.
