    Application security reference¶

    This guide describes authentication and authorization for one-shot generated SOAD applications. It is intended for application developers, deployers, and operators.

    Architecture and production boundary¶

    app/s0adm/ is the online IDE and control plane. It is not an authentication service for deployed applications and must not be included in production images.

    Generated applications use one of these modes:

    Mode Identity source When to use it
    local The application's own datasource and the framework auth runtime Protected applications; this is the default
    custom An application transaction implementing the provider interface SSO, OIDC, an existing account system, or another replacement
    public No identity provider Applications whose security profile is entirely public

    In local mode the framework supplies login/logout, password reset, invitations, TOTP, profiles, session revocation, user administration, CSRF protection, and role/permission enforcement. Its routes are under /_soad/auth/*; it does not import or query s0adm.

    IDE sessions use keys such as s0uid. Application sessions use distinct soad.auth.* keys and a revocable record in the application database. An IDE login is therefore never accepted as an application login.

    Generation defaults¶

    One-shot generation infers a security profile from the business requirements:

    Application Profile and mode
    CRM, ERP, HR, invoicing, internal CRUD, dashboards, private/customer data authenticated + local
    Landing pages, documentation, brochure sites, genuinely public catalogs public + public
    Public content plus staff/customer workflows mixed + local
    Ambiguous brief authenticated + local

    Operators can disable this inference with:

    ai.one.shot.auto.security = false

    The equivalent environment variable is ai_one_shot_auto_security=false. When disabled, one-shot generation uses public access without a login unless the product prompt explicitly requests authentication or access control. Explicit requests for login, private or protected access, accounts, roles, or permissions still produce the appropriate authenticated security plan. The default is true; restart the IDE after changing the property or environment variable.

    Local registration is invite_only unless the brief explicitly requires open registration. Open registration requires a least-privilege member role, which is granted to new accounts; it never grants admin. The generator does not create login, password, session, user, or ACL code inside business transactions.

    The accepted plan produces:

    • WEB-INF/security/app-security.json, the immutable runtime security manifest;
    • WEB-INF/deploy/auth-mysql.sql, the production installation bundle;
    • WEB-INF/deploy/auth-h2.sql, the development/test installation bundle.

    These artifacts come from the same normalized plan. The SQL contains schema, roles, and permissions but never users, password verifiers, invitations, sessions, or other secrets.

    Manual setup (without one-shot generation)¶

    An existing or hand-built app has no app-security.json until you configure one. Do this from the IDE, without the AI assistant:

    1. Open Settings → Application for the app.
    2. If the app has no security metadata yet, the Security card shows a profile/mode picker instead of the read-only summary. Choose:
    3. Security profile — public, authenticated, or mixed.
    4. Authentication mode — local (framework-managed users in the app's own database) or custom (your own provider transaction). public mode is only offered when the profile is also public.
    5. Authenticated and mixed profiles require at least one role. Enter it in the initial Roles editor:
    admin|Administrator|Full access
member|Member

    The example above expresses code, name, and description; enter these in the corresponding role row fields. Only the role code is required (lowercase, starts with a letter, e.g. [a-z][a-z0-9_.:-]*); name defaults to the code and description is optional. Leave the box empty for a public profile — public profiles must not declare roles. 4. Save. This validates the plan, writes the manifest and both SQL bundles, and — for local mode — installs the local-auth schema into the app's database immediately and grants your IDE account system_admin plus the first listed role. A one-time, 20-minute setup link to set your local password is shown on the page; do not share or log it.

    Initial setup creates roles without business permission grants. After saving, open the application's Roles and permissions section to register permission codes and assign grants to roles. The editor audits controller policies and identifies missing permission codes. Save to publish the updated manifest and install matching development metadata. Do not confuse this editor with the platform's IDE Roles screen. The transaction-editor AI path below is another way to stage a complete security plan.

    Switching auth_mode later (once a profile exists) uses the same Security card without re-entering roles — see Switching providers.

    Alternative: the per-transaction editor AI (superadmin only)¶

    Besides the Settings form above and one-shot generation, a superadmin can also have the AI assistant propose a security plan while editing transactions in a normal (non-one-shot) chat session — including full roles and permissions:

    • The chat session exposes a stage_app_security tool only when session.security_management is true, which the server sets from is_superadmin(user_id) on every chat session (app/s0adm/ai/chat.py, set_security_management). Non-superadmins never see this tool; regular one-shot generation sessions reject it too — one-shot uses its own embedded plan instead.
    • Asking the assistant to set up or change roles/permissions/profile calls stage_app_security (app/s0adm/ai/tools.py, _stage_app_security), which builds and validates the manifest, checks that no already-assigned role would be orphaned, and audits every routed transaction's ACCESS_POLICY against the proposed plan — but only stages it. Nothing is written yet.
    • The staged plan appears in the normal diff/approval UI alongside any staged code changes. Approving it (app/s0adm/ai/chat.py, approve) re-checks that the approver is a superadmin, then calls the same security_mod.configure_app_security(...) used by the manual form — so the effect (manifest + SQL bundles written, local-auth schema installed, setup link issued) is identical either way.

    Use this path when you want AI help drafting roles/permissions/rationale. The manual application Roles and permissions editor also supports those grants.

    Controller contract¶

    Each routed controller method needs an exact ACCESS_POLICY entry:

    class Contact(object):
    ACCESS_POLICY = {
        "view": "permission:contacts.read",
        "save": "permission:contacts.write",
    }

    def view(self, ctx):
        current_user = ctx.output.get("current_user")

    def save(self, ctx):
        """POST"""
        pass

    Policy values are:

    • public;
    • authenticated;
    • permission:<manifest-permission-code>.

    Use the provider-neutral template values:

    {{#if current_user}}
  <span>{{current_user.full_name}}</span>
  <a href="{{logout_url}}">Sign out</a>
{{else}}
  <a href="{{login_url}}">Sign in</a>
{{/if}}

<input type="hidden" name="csrf_token" value="{{csrf_token}}">

    current_user is in ctx.output; it is not an attribute of ctx. Never use ctx.current_user or getattr(ctx, "current_user", None).

    Deploying local authentication¶

    Only MySQL production databases and H2 development/test databases are supported initially. Generation and installation reject other dialects.

    1. Build the runtime base, which intentionally does not copy app/s0adm/:
    docker build -f app/Dockerfile-base-runtime \
  -t your-registry/soad-runtime:VERSION app

    1. Build the generated application layer using app/Dockerfile-runtime and that base image.

    2. Extract or obtain WEB-INF/deploy/auth-mysql.sql from the generated workspace/image and apply it explicitly to the application database before rollout:

    mysql --host DB_HOST --user DB_USER --password --database APP_DATABASE \
  < webapp/WEB-INF/deploy/auth-mysql.sql
    1. Configure the runtime datasource through environment variables:
    db_default_url
db_default_driver_class
db_default_username
db_default_password
    1. Create the first application administrator with password input on stdin:
    printf '%s\n' "$INITIAL_PASSWORD" |
  docker exec -i APPLICATION_CONTAINER \
    soad-auth-admin create-admin \
    --app default \
    --email admin@example.com \
    --name "Application Administrator" \
    --password-stdin

    Prefer a secret-file/stdin mechanism that does not place the password in shell history. The CLI refuses password arguments, validates the manifest and installed schema checksum, and grants both system_admin and the generated owner/admin role.

    1. Check readiness:
    GET /_soad/auth/health

    It returns 200 only when the installed schema version and manifest checksum match the image. A protected route returns 503 instead of running unauthenticated when SQL has not been applied.

    The production configuration is app/conf/sufia-runtime.properties. It contains the application transaction and auth servlets only. It has no db.s0adm, /s0adm/t/*, IDE listener, IDE static mapping, extra Jython path, file editor, database editor, AI endpoint, deployment screen, or log servlet.

    Development setup¶

    When one-shot generation publishes a protected application, the IDE explicitly installs the appropriate MySQL/H2 bundle into the development application database. It creates an application-local record matching the developer's email but does not copy the IDE password or trust the IDE session.

    The authenticated generation completion includes a 20-minute, single-use setup URL. Opening it sets a separate local password. Do not publish this URL in logs, source control, chat history, or deployment artifacts.

    Built-in pages and administration¶

    The local provider exposes:

    Route Purpose
    /_soad/auth/login, /logout Session creation and revocation
    /_soad/auth/bootstrap Initial administrator setup when none is active
    /_soad/auth/register Open registration when enabled
    /_soad/auth/forgot, /reset Generic, single-use password recovery
    /_soad/auth/invite Invitation acceptance and initial password setup
    /_soad/auth/profile, /password Profile and password changes
    /_soad/auth/totp/setup Authenticator-app enrollment/removal
    /_soad/auth/sessions List and revoke active sessions
    /_soad/auth/admin/users Invite, enable/disable, and assign roles
    /_soad/auth/health Schema/manifest readiness

    system_admin includes the reserved auth.users.manage permission. Generated business roles are separate. Disabling a user or resetting a password revokes their active sessions.

    SMTP is optional for local development. When it is not configured, an administrator can copy the invitation link from the result page. Production password recovery requires mail configuration. Set sufia_hostname to the public HTTPS origin (for example, https://app.example.com) when the runtime is behind a reverse proxy so emailed links use the external address.

    Customizing built-in authentication pages¶

    Local authentication supports validated Handlebars overrides under:

    webapp/WEB-INF/auth-overrides/

    The supported files are login.html, verify-totp.html, register.html, bootstrap.html, forgot.html, reset.html, invite.html, profile.html, sessions.html, totp-setup.html, admin-users.html, and error.html. A shared stylesheet may be placed at webapp/assets/auth-overrides/auth.css. Public mode has no login UI, and custom providers own their complete login flow.

    Every page receives escaped common values including:

    {{title}}
{{csrf_token}}
{{message}}
{{error}}
{{context_path}}
{{default_stylesheet_url}}
{{stylesheet_url}}

    Page contexts also provide their action/navigation URLs and applicable token, user, role, TOTP, or session-list data. Existing login placeholders such as {{action_url}} and {{forgot_url}} remain supported.

    admin-users additionally provides {{create_action_url}} for the add-user form, whose fields are full_name, email, the optional password and password_confirm, and a repeated role_codes checkbox per entry in {{roles}}. Leaving both password fields empty creates the account pending and issues a one-time setup link, returned as {{invite_link}}; each entry in {{users}} carries a pending flag for that state. These inputs are optional in an override — a template that omits them keeps validating, and simply does not offer the feature.

    Overrides are limited to 128 KiB per HTML page and 256 KiB for the stylesheet. They must compile, retain the page's required form actions and input names, and render {{csrf_token}} for state-changing forms. Executable URLs, frames/objects, <base>, and unescaped triple-brace values are rejected on every screen. So is any URL pointing at another origin: an https://, http://, or //host value in href/xlink:href/src/action/formaction, or in an @import/url() in the stylesheet — no CDN stylesheet, remote image, font host, or off-site form target. Relative paths, {{context_path}}/…, #fragment, mailto:, and data: URIs of image or font types are unaffected. A missing or invalid file logs a warning and falls back to the framework page.

    Script is allowed by screen, not globally:

    • The four signed-in management screens -- profile, sessions, totp-setup, admin-users -- accept an inline <script> and inline event handlers. They are reached only after _require_user (and, for admin-users, the auth.users.manage permission), so the reader is already authenticated, and these list-and-row pages want a modal or a disclosure toggle to be usable.
    • Every other screen is shown to an anonymous visitor and rejects both, because script there can read the password field and the CSRF token.
    • No screen accepts script from outside the application. <script src=...> and <script type="module"> (whose import can fetch remote code with no src) are rejected everywhere: a fetched script can change under the deployment, and it fails entirely in an air-gapped install.

    The four relaxed routes also carry a Content-Security-Policy response header (script-src 'self' 'unsafe-inline', connect-src 'self', object-src 'none', frame-ancestors 'none') so the browser enforces the same in/out distinction on what a regex over the markup cannot see -- a remote import() or fetch() from inside a script body. The sign-in flow sends no CSP.

    The transaction-editor AI stages these files through the normal diff and approval workflow. Deleting an override restores the framework default. An override changes presentation only; it never replaces credential verification, sessions, CSRF, roles, or permissions.

    For different authentication behavior rather than different styling, use a custom provider.

    Changing the logo¶

    The narrow, single-purpose screens (sign in, register, forgot, reset, invite, verify-2FA, error) show a small mark above the title. By default this is the framework's own SOAD icon; a developer can replace it by placing a bare, self-contained SVG at:

    webapp/WEB-INF/auth-overrides/mark.svg

    This is validated like the other overrides but is not a Handlebars template -- it is inlined as-is into the page, once per narrow screen, so it has its own, narrower rules:

    • The whole file must be a single <svg>...</svg> element: no XML declaration, <!DOCTYPE>, or entity, and nothing before/after the root tag.
    • No <script>, inline event handlers (onload, onclick, ...), frames, <object>/<embed>, or <foreignObject> (which can smuggle arbitrary HTML/script inside an SVG).
    • href/xlink:href may only point at a local #fragment (e.g. a <use> referencing a <symbol> defined earlier in the same file) -- no external file or data: URL, keeping the mark a single self-contained asset for air-gapped deployments, same as everything else this stylesheet ships.
    • Limited to 24 KiB.

    Any class/aria-hidden attribute on the root <svg> is stripped and replaced by the framework (class="auth-mark" aria-hidden="true"), so sizing comes from the page's own CSS regardless of what the file declares -- set a viewBox and skip width/height on the root element and let the page size it. A missing or invalid mark.svg falls back to the framework mark, same as any other override. The transaction-editor AI can stage it too, via stage_auth_override with screen: "mark". Wide management screens (profile, sessions, 2FA, admin users) never show the mark, override or not.

    Switching providers¶

    In the IDE, open Settings → Application and choose:

    • Application-local identity;
    • Custom application provider;
    • Public, available only for a public profile.

    Saving the setting regenerates the manifest and both SQL bundles. Controllers and their ACCESS_POLICY declarations do not need to change.

    Custom provider interface¶

    Set the module to a lowercase application transaction path such as security/auth_provider. Its class must implement:

    class Auth_provider(object):
    def current_user(self, ctx):
        return None

    def authenticate(self, ctx):
        return None

    def authorize(self, ctx, action, permission):
        return False

    def validate_csrf(self, ctx):
        return False

    def login_url(self, ctx):
        return "%s/t/security/login" % ctx.ctxPath

    def logout_url(self, ctx):
        return "%s/t/security/login/logout" % ctx.ctxPath

    The provider transaction itself is not routable through the transaction engine. Methods fail closed: protected actions require a non-null authenticated user, permission checks require exactly True, and protected mutations require exactly True from validate_csrf.

    Switching to custom or public stops loading the built-in local provider. The reserved local tables may be left in place for an easy rollback or removed later through an operator-reviewed database migration; the runtime never drops them.

    Security behavior¶

    • Passwords use PBKDF2-HMAC-SHA256, a random per-user salt, 600,000 iterations, and stored algorithm/cost metadata.
    • Login attempts are rate-limited and responses do not disclose whether an account exists.
    • Reset/invitation tokens are random, stored only as SHA-256 hashes, expire, and are single-use.
    • Protected local mutations require CSRF validation; public business mutations must validate CSRF explicitly. Built-in auth forms validate their own tokens.
    • Return URLs must be same-application absolute paths.
    • Authentication rotates the HTTP session ID and CSRF token.
    • Runtime sessions are revocable database records, not merely browser session attributes.
    • The shipped production profile uses HttpOnly, SameSite=None, and Secure. The tracker deployment explicitly selects Lax for its same-site flow.

    The runtime image build also fails when /app/s0adm exists or generated application source imports or links to s0adm. In a valid production image, /s0adm/* has no mapping and returns 404.
