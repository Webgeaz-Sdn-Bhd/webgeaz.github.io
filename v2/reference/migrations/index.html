    Database migrations and older installations¶

    There are two separate database lifecycles: S0ADM's control-plane schema and your application's business/auth schema. Choose the intended database before running any SQL.

    Existing S0ADM installations¶

    New IDE databases are initialized from app/s0adm/setupdb-s0adm.sql when empty. An existing database is not rebuilt by restarting an image. Review the numbered SQL files under app/migrations/ against your installed columns and migration history:

    File Feature
    001_ai_chat.sql AI conversations
    002_user_2fa.sql IDE second-factor fields
    003_user_avatar.sql Profile avatar
    004_app_security.sql Application security metadata
    005_custom_auth_provider.sql Provider selection
    006_ai_provider_settings.sql IDE AI provider settings
    007_security_rationale_length.sql Expanded rationale
    008_ai_auto_accept.sql AI auto-accept setting
    009_user_ui_theme.sql User theme preference

    Back up before changes. The migration files are not a promise that every SQL dialect accepts every statement or that an already-applied file can be rerun. For local H2 using dev.sh, stop the app before migrate:

    ./dev.sh stop
./dev.sh migrate app/migrations/002_user_2fa.sql
./dev.sh start

    Use the appropriate unapplied migration, not necessarily 002. Check the script's database target. External H2 access while a process is running requires compatible AUTO_SERVER settings; stopping the local process avoids file-lock ambiguity. For MySQL use your normal reviewed migration client.

    The historical README's 2FA guidance has been consolidated here. Its key requirement remains: existing installs need the schema update and refreshed models, not just new application files.

    Application migrations¶

    Keep ordered, version-controlled business SQL in your application project. The tracker initial schema is for a fresh database; evolve it using new migrations rather than editing and replaying the initial script.

    Local-auth generation produces auth-mysql.sql and auth-h2.sql beside the security manifest. Install the bundle for your dialect. The manifest checksum must match installed metadata; changing roles/permissions requires compatible metadata deployment, not just controller edits.

    Auth bundles contain schema/role/permission metadata, not users or secrets. Review grant changes because reinstalling metadata can change effective access. Back up user/session data separately.

    Deployment order¶

    1. Back up and confirm the target database.
    2. Apply reviewed auth/business migrations.
    3. Start the matching image so models regenerate.
    4. Check auth health and application behavior.

    Rollback must pair a compatible image, manifest, and database state. MySQL DDL may commit implicitly; a failed migration is not necessarily automatically undone.
