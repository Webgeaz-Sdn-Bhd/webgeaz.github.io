    7. Build the project/task tracker¶

    This chapter connects the database, transaction, and view concepts into one application. The complete source is included so you can compare your work at each stage.

    1. Prepare identity and data¶

    Complete the setup, then configure the five permissions and grants in the plan. Install schema.sql in the application's database and run Introspect. The Project, Task, Attachment, and Soad_auth_user models must be available before the controllers import them.

    Create transactions in this order:

    Group/code Controller Views
    tracker/layout Layout layout.html
    tracker/project Project project.html, edit.html
    tracker/task Task task.html, edit.html

    Copy their contents from the example's webapp/WEB-INF/jython/default/tracker/ directory. For the CLI use soad create and then place source in the nested CLI layout described in chapter 12.

    2. Create and list projects¶

    Project.view reads only rows whose owner_id equals ctx.output["current_user"]["id"]. Its query binds the search value and limits results to 20 plus one look-ahead row.

    Project.save trims and checks the name before writing. A new project's owner is taken from the authenticated context, never from a hidden form field. An existing project is loaded with both its ID and owner ID.

    Open /t/tracker/project, create “Website launch”, and confirm it appears. Edit its name. Submit an empty name with browser validation bypassed and verify the controller returns feedback without creating a row.

    3. Add tasks and assignment¶

    Task imports the project's private ownership helpers. Every task action loads the requested project through that ownership check before loading a task. A task is then looked up by both id and project_id, preventing a caller from combining their project ID with somebody else's task ID.

    Create “Write homepage”, assign an active application user, and change its status through todo, doing, and done. The server rejects any other status and rejects nonexistent or disabled assignees. The assignee selector passes only ID and display name to the view, not entire authentication records.

    Invite a second application user through /_soad/auth/admin/users to populate the selector. Assignment is a label, not project membership.

    4. Add presentation and navigation¶

    Build and upload the example's CSS as described in its README. The layout provides navigation, profile/sign-out links, a skip link, and a content area. Forms preserve submitted values on errors. Tables scroll on narrow screens.

    Set the default application's Welcome transaction to tracker/project in System Settings. Its persisted release setting is WEB-INF/sufia-app.properties; an operator's sufia_welcome_transaction environment override takes precedence.

    5. Add attachments and JSON¶

    Upload a small text file while saving a task. Download it through the task's authorized download action. Removing or replacing an attachment happens within the database transaction. The example deliberately serves bytes as an attachment, with application/octet-stream and nosniff.

    Visit:

    /t/tracker/task/data?project_id=PROJECT_ID

    You should receive a JSON object containing a bounded task list, page number, and has_next. This endpoint uses the same login and ownership rules as HTML; it does not automatically become a bearer-token API.

    6. Prove the access rules¶

    Use two separate browser sessions. Create a project as user A; sign in as member B and request A's project edit URL, task URLs, and attachment URL. Each must deny access without returning A's data.

    As a member, POSTing project deletion should return 403 even for your own project. As an administrator, deletion of your own project succeeds and cascades to tasks/attachments. An administrator still cannot delete somebody else's project through this tutorial's routes.

    The delete controls disclose the action and consequence before the final submit. The server policy is authoritative even when a control is visible.

    Completion¶

    You now have a complete CRUD application with separate accounts, data ownership, roles, assignment, filtering, pagination, uploads, and JSON output. Run the acceptance checks before following the deployment chapters. Team sharing, notifications, and optimistic concurrency are deliberate extension exercises, not hidden requirements of the supplied implementation.
