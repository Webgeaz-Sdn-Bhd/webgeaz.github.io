    8. Built-in authentication: use, configure, and override¶

    SØAD supplies application-local login and authorization. The application's users, roles, permissions, tokens, and revocable sessions live in its own datasource. An S0ADM login does not authenticate a user to your web application.

    Choose a mode¶

    Profile / mode Use
    authenticated / local Protected application using built-in accounts
    mixed / local Public pages plus protected actions
    public / public Entirely public application, without a login provider
    authenticated or mixed / custom Your provider owns identity and authentication

    The security manifest at WEB-INF/security/app-security.json defines the application's mode, roles, permission grants, and registration policy. Changing a controller policy does not register its permission automatically.

    flowchart TD
    Request --> Manifest{Security metadata ready?}
    Manifest -->|No| Unavailable[503]
    Manifest -->|Yes| Policy{Action policy}
    Policy -->|Missing| Denied[403]
    Policy -->|Public| Action[Run action]
    Policy -->|Protected| Identity{Signed in?}
    Identity -->|No| Login[Login redirect]
    Identity -->|Yes| Checks[Check CSRF for mutation and permission]
    Checks -->|Denied| Denied
    Checks -->|Allowed| Owner[Application ownership validation]
    Owner --> Action

    Set up the built-in provider¶

    1. Open System Settings → Applications → your application as an IDE superadmin.
    2. Initialize the Security card with authenticated, local identity, and roles admin and member. Save and follow the one-time application-password link.
    3. Open that application's Roles and permissions section. Add the codes from the tracker plan and select their grants. Save to publish the manifest and install matching development metadata.
    4. Keep registration invite_only for this tutorial. Open registration requires a least-privilege member role and must not grant administrator access.
    5. Test an application route with the new application account.

    Initial role setup and later permission editing are different forms. The platform-level Roles screen controls IDE access; it is not the application's permission editor. An unregistered permission:code denies every user; inspect the application's policy audit and logs if even an administrator receives 403.

    Protect controllers and records¶

    class Project(object):
    ACCESS_POLICY = {
        "view": "permission:projects.read",
        "save": "permission:projects.write",
        "delete": "permission:projects.delete",
    }

    Use public, authenticated, or permission:<registered-code> for each action. Set POST/PUT/DELETE method docstrings on mutations. Authenticated local mutations accept the csrf_token form field or CSRF-Token request header. For JSON, put the token in the header, not only inside the JSON body.

    Public local-auth actions receive a token in the template context, but the business action must validate CSRF itself for public state changes. The runtime's protected-action check does not make public writes safe automatically.

    Policies decide whether a caller may run an action. Your query must still enforce record ownership, organization membership, or other business access rules.

    Built-in pages and settings¶

    Route under /_soad/auth Purpose
    /login, /logout Sign in and sign out
    /bootstrap First administrator setup, gated by absence of an active admin
    /register Self-registration when enabled
    /forgot, /reset Password recovery
    /invite Invitation and initial password setup
    /profile, /password Profile/password management
    /totp/setup TOTP enrollment/removal
    /sessions List/revoke sessions
    /admin/users Account creation, invitations, status, roles
    /health Manifest/schema readiness

    Create the first production admin with soad-auth-admin before exposing the service, or complete the bootstrap page on a restricted setup connection. Browser bootstrap grants system_admin; use its user administration page to grant the business admin role afterward. The administrative CLI also grants the manifest's generated owner/admin role. Use invitation setup links as secrets. Password resets and account disabling revoke active sessions. TOTP is implemented; do not describe it as future work.

    Configure sufia_hostname as the public HTTPS origin and sufia_app_name as the display name. SMTP uses mail_smtp_host, mail_smtp_port, mail_smtp_username, mail_smtp_password, and mail_sender_email. See the mail transport limitation in integrations.

    The checked-in production profile has session.cookie.secure=true, session.cookie.httponly=true, session.cookie.samesite=NONE, and a 1,800-second idle timeout. This guide's same-site tracker deployments explicitly choose LAX; keep NONE only when your cross-site flow needs it and always use HTTPS. The local auth session record also has its own expiry; changing the servlet idle timeout does not change that database session lifetime.

    Override appearance without replacing authentication¶

    Put validated templates under WEB-INF/auth-overrides/; shared CSS belongs at assets/auth-overrides/auth.css. Start with login.html, and retain its field names, action URLs, CSRF field, and required page structure.

    A template is not an ordinary application view: the override validator permits only its supported template/markup contract. Do not reuse the tracker layout or load a CDN. Use the full screen-by-screen contract for the exact required inputs and context for every screen, including bootstrap.

    Override mark.svg to replace the small-screen logo. Missing or invalid templates/styles/marks fall back to the bundled UI and log the reason. Removing an override restores the default. Presentation overrides do not change password, session, or permission verification.

    Replace authentication behavior¶

    Choose Custom application provider and a lowercase module such as security/auth_provider. Its Auth_provider class must implement:

    Method Contract
    current_user(ctx) Current identity or None
    authenticate(ctx) Authenticated identity or None
    authorize(ctx, action, permission) Exactly True to grant the permission
    validate_csrf(ctx) Exactly True to accept a protected mutation
    login_url(ctx), logout_url(ctx) URLs for your authentication flow

    The provider module is not directly routable. Put login/callback actions in separate transactions with explicit policies. A custom provider must supply credential verification or a complete external identity integration, session handling, revocation, callback/return validation, and CSRF behavior. Selecting custom does not install OIDC or SSO automatically.

    See the provider skeleton and fail-closed rules. The skeleton deliberately grants nothing until implemented. After changing modes, publish matching metadata/SQL and test before deploying. Keep old local tables during an initial rollback window; the runtime does not drop them automatically.

    Transaction-owned auth pages are an advanced local-provider integration, distinct from templates and custom providers. Their route mapping must be registered in the manifest; do not implement a second password store or assume the archived roadmap is a current API contract.
