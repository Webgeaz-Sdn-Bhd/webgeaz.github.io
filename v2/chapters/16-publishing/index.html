    16. Put this documentation online¶

    The Markdown under docs/ is the source of truth. The repository's mkdocs.yml builds a static website with Material for MkDocs, chapter navigation, search, code highlighting, and Mermaid diagrams.

    Preview and build¶

    From the repository root:

    python3 -m venv .venv-docs
.venv-docs/bin/python -m pip install -r requirements-docs.txt
.venv-docs/bin/mkdocs serve

    Open http://127.0.0.1:8000. On Windows use the virtual environment's Scripts directory in place of bin. The docs tooling uses Python 3; this is independent of application Jython 2.7. See Material installation for platform alternatives.

    Build and validate:

    .venv-docs/bin/mkdocs build --strict

    The resulting site/ directory is the deployable website. Do not host mkdocs serve as a production service. Before publishing, set site_url in mkdocs.yml to the final URL, including a path prefix if applicable, for example https://docs.example.com/soad/.

    Option A: GitHub Pages¶

    Put the documentation repository on GitHub, enable Pages in repository Settings, and use a dedicated gh-pages branch as the publishing source. From an authorized checkout with Git push access:

    .venv-docs/bin/mkdocs gh-deploy

    This builds the site and pushes its generated contents to the publication branch. It does not deploy your SØAD application. For a private source repository, confirm your GitHub plan's Pages visibility and access rules before publishing.

    For automatic publication, adapt the optional workflow below and save it as .github/workflows/docs.yml only when you want pushes to publish:

    name: Publish documentation
on:
  push:
    branches: [main]
    paths: ["docs/**", "mkdocs.yml", "requirements-docs.txt"]
  workflow_dispatch:
permissions:
  contents: write
jobs:
  docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: python -m pip install -r requirements-docs.txt
      - run: mkdocs build --strict
      - run: mkdocs gh-deploy

    Change main to your actual publication branch and review action versions/pins under your organization's CI policy. This example is documentation, not an enabled workflow. See Material's publishing guide for the host setup.

    Option B: any static web host¶

    Upload the contents of site/ to your static host's document root, bucket, or artifact deployment. Configure HTTPS, directory index support, and the base path corresponding to site_url. For a managed build service:

    Setting Value
    Install python -m pip install -r requirements-docs.txt
    Build mkdocs build --strict
    Output site

    With an existing web server, serve the generated HTML/assets as ordinary files. Do not expose the repository root, .git, runtime configuration, or databases. For a custom domain configure the host's domain binding, DNS, and TLS certificate.

    Diagrams, search, and offline environments¶

    Mermaid fences render through the theme's diagram integration. Diagram JavaScript may need network access in a browser. For an air-gapped host, package a reviewed local Mermaid asset and configure local loading, or pre-render diagrams to SVG as part of your site's build. Test actual deployment CSP/network rules; a successful Markdown build alone does not prove diagrams render.

    Open the hosted site over HTTP(S), not just as file:// pages, to test search and asset loading. Text beside each diagram explains the same relationship for readers whose renderer does not support Mermaid.

    Maintain the chapters¶

    Update navigation when adding a page. Use relative .md links and stable headings; run strict builds after moves. Update the example, configuration reference, and acceptance cases whenever a framework contract changes.

    The maintainer archive is deliberately excluded from both publication and search. It preserves historical implementation notes and old root content; do not copy it into public navigation as current product documentation. Example verification tools/tests are also excluded from the generated site.

    Before publishing check the home page, one code-heavy chapter, authentication, deployment, search, mobile navigation, and all diagrams. The numbered chapters remain readable as Markdown if you decide to change site generators later.
