    16. Publish application documentation¶

    Application documentation should travel with the application release without requiring access to the SØAD framework source. Write documentation in your own workspace, publish it through your organization's normal documentation service, and link it from the application where useful.

    Choose what to publish¶

    Useful application documentation includes:

    • user workflows and role-specific capabilities;
    • application URLs and supported browsers;
    • administrator setup and recovery procedures;
    • business-schema migration order;
    • application configuration that operators must supply;
    • health checks, backup expectations, and rollback constraints.

    Do not publish IDE credentials, application passwords, API keys, database credentials, invitation tokens, private hostnames, or generated security artifacts containing environment-specific details.

    Keep release information together¶

    Record the following for each application release:

    Item Purpose
    Application version Identifies the transaction and asset release
    SØAD runtime version Identifies the compatible runtime container
    CLI version Helps reproduce source synchronization behavior
    Image digest Identifies the exact deployed container
    Business migration version Identifies the expected application schema
    Security manifest checksum Identifies matching authentication metadata

    The S0ADM release/export workflow and the soad CLI are the application source boundaries. Documentation may describe their commands, but should not assume the reader has framework internals, build scripts, or the SØAD product source tree.

    Publish safely¶

    Build your documentation using the tooling selected by your organization, then upload only its generated public output to the documentation host. Keep source configuration, credentials, local CLI configuration, databases, and temporary release artifacts outside the public document root.

    For internal applications, apply the same access-control expectations to the documentation site. A public documentation URL can disclose routes, roles, data models, and operational details even when the application itself is protected.

    After publication, verify links, search, mobile layout, authentication boundaries, and any command examples against the deployed development environment. Update the documentation whenever transaction behavior, roles, permissions, migrations, or runtime requirements change.
