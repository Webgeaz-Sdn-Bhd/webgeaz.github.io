    13. Testing and completing the application¶

    Test behavior at the boundary where it matters. A successful compile or HTTP 200 does not prove that a protected application works correctly.

    Test layers¶

    Layer What to verify
    Pure validation Lengths, identifiers, allowed status values
    Jython and database Generated models, queries, ownership, cascades, rollback
    HTTP Routing, method guards, authorization, CSRF, redirects, content type
    Browser Forms, errors, saved values, downloads, narrow-screen usability
    Deployment Image content, installed schema/manifest, readiness, persistence

    The tracker includes an isolated JVM/H2 test script. See its README for the command and exactly which boundaries it covers.

    Framework-maintainer checks from this repository:

    ./dev.sh test

    These are offline JUnit/Jython checks with H2. Browser integration uses ./dev.sh test-ide-ui; test-ide-all also runs HTTP smoke checks. Those commands need the container/browser environment and test the IDE, not automatically every application you create.

    Tracker acceptance checklist¶

    1. Anonymous requests redirect to application login; an IDE session alone is insufficient.
    2. Admin and member accounts can create/edit their own projects and tasks.
    3. Invalid name/title/status produces feedback and no partial update.
    4. IDs for another owner are rejected on list details, edit, save, delete, JSON, and download paths; a task cannot be moved by submitting another project ID.
    5. A member cannot invoke the project-delete route. Administrator access still obeys ownership.
    6. Missing/incorrect CSRF tokens fail on protected mutations. GET requests to save/delete do not change data.
    7. Pagination is stable; filtering stays active when moving between pages.
    8. A disabled/nonexistent assignee is rejected. Assignment alone grants no access.
    9. Small uploads download as attachments; oversize uploads fail; replacement, removal, task deletion, and project deletion remove the expected blob rows.
    10. HTML-like titles display as text; quotes/newlines in filenames do not create response headers. JSON contains only selected fields.
    11. Failed login, logout, reset, and revoked sessions behave correctly. Test recovery email and TOTP with disposable accounts.
    12. After restart, database records remain; session persistence follows the deployment's configured storage and expiry.

    Before release¶

    Record the framework/CLI version, application source version, business migration version, image digest, and security manifest checksum together. Back up the application database and test restoration. Apply SQL only to the intended environment. Confirm the runtime contains no IDE directory, IDE database, development account credentials, or provider API keys.

    Use production mode, HTTPS, secure cookies, configured public origin, and bounded upload settings. Exercise /_soad/auth/health and a real protected page after installing auth SQL.

    Failure and rollback¶

    A source rollback is not a database restore. If a deployment changes auth metadata, old and new manifests may not both match the installed checksum. Plan a maintenance window or an explicitly compatible migration; the example's single-replica deployment uses Recreate and permits downtime.

    For a failed rollout, restore a known image and its compatible metadata/schema. Never rerun an initial business CREATE TABLE script against a populated database as a substitute for a migration.
