    11. S0ADM features, including AI¶

    S0ADM is the browser development environment for SØAD. Use it to create and test applications, manage development metadata, and prepare releases. Keep it on a restricted development/control-plane instance.

    Workspace and application tools¶

    Feature Developer workflow
    Applications/settings Select/configure apps, developer access, security, welcome route
    Transaction editor Create group/code, edit Jython and views, save/compile, preview
    Editor workspace Open multiple transactions/files, switch tabs, retain drafts
    Versions Inspect prior transaction saves and restore a selected version
    File manager Browse folders, create/upload/rename/edit/download application files
    Database explorer Inspect schema, tables/columns, records, DDL, query results
    SQL editor Execute reviewed SQL, inspect history/results, refresh generated models
    Logs Diagnose compile/runtime/database errors
    People and profile IDE users/roles, access, profile, sessions, and account security
    Gallery Discover/import packaged application content where configured
    Release/deployment Prepare an application image and view build progress

    Saving transaction source is not the same as applying database DDL. When adding a column, update the schema, refresh models, then save the controller and template. Unsaved editor drafts are not deployed source; check the saved version before export or release.

    System settings and deployment actions require elevated IDE privileges. Features also depend on the image, license, datasource, and installed tools. The deployment screen reports unavailable builds when Kaniko is absent; a standalone image does not imply in-cluster builds are enabled.

    Configure the AI assistant¶

    As superadmin, open System Settings → Applications → an application → AI assistant. Configure provider family, endpoint, API key, model, and enabled state. These settings are platform-wide, even when reached from one application's page.

    Supported wire families are OpenAI-compatible chat completions, OpenAI Responses, and Anthropic messages. Use a model available from your configured provider; the guide does not pin a changing provider model catalog.

    Property Environment variable
    ai.enabled ai_enabled
    ai.provider ai_provider
    ai.endpoint ai_endpoint
    ai.api.key ai_api_key
    ai.model ai_model
    ai.auto.accept ai_auto_accept

    Resolution is per field: saved IDE settings, then environment, properties, and built-in default. Auto-accept defaults off. Restart for property/environment changes. Keep secrets in managed configuration rather than pasted application code.

    Understand the two AI workflows¶

    Transaction editor chat: open a transaction and choose AI/Edit with AI. Ask it to read code, diagnose logs, propose changes, or restore versions. Ordinary source edits are staged for diff review; Approve & Execute publishes them. Auto-accept can automate eligible approvals when enabled.

    Dashboard whole-app generation: describe a complete app on a suitable empty application. This has a separate server-authorized workflow: it can execute SQL, install provisional transactions, review and validate them, and publish the result. Do not assume that no database or source changes occur before final publication. Follow the visible workflow state and use a disposable development database for a first attempt.

    flowchart TD
    Prompt --> Mode{Development workflow}
    Mode -->|Editor chat| Read[Read source and schema]
    Read --> Stage[Stage changes and show diff]
    Stage --> Approval[Manual approval or enabled auto-accept]
    Approval --> Save[Save changes]
    Mode -->|Whole-app generation| Plan[Prepare app and security plan]
    Plan --> Build[Authorized schema and provisional source changes]
    Build --> Validate[Review and runtime validation]
    Validate --> Publish[Publish or report failure]

    Normal chat SQL blocks have an Execute action for the developer. Rename/move is an immediate tool operation with conversational confirmation semantics; check internal links afterward. These are different from staged file editing. See AI workflows for details.

    A useful tracker prompt¶

    Build an authenticated project/task tracker using local application identity. Members own projects and may manage tasks in their own projects. Assignment does not grant access. Register projects.read, projects.write, tasks.read, tasks.write for admin/member, and projects.delete for admin. Check ownership on HTML, JSON, and download actions. Use Jython 2.7, Handlebars, and local compiled Tailwind assets. Show the schema and review the access rules.

    For larger work, use the planning guide to create a schema, route/action list, acceptance criteria, and phases before generation. Project AGENTS.md conventions help preserve naming and design choices.

    Review generated SQL, permissions, uploads, and business validations just as you would review manually written code. Model output and runtime validation are not a substitute for testing with different user accounts.
