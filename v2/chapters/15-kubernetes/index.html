    15. Deploy with Kubernetes¶

    The example manifest deploys one tracker replica with a Service, TLS Ingress, configuration, and a session PVC. It assumes an existing MySQL database and an installed Ingress controller.

    Prepare the cluster inputs¶

    1. Build/push the application image from chapter 14.
    2. Create the application database and apply the release's auth SQL and business migrations using your normal database administration connection.
    3. Replace the example image, database hostname, public hostname, Ingress class, and resource/storage settings. Supply imagePullSecrets if the registry needs it.
    4. Create a TLS Secret named tracker-tls, or configure your certificate manager to create it. Point the public DNS record at the Ingress endpoint.
    5. Create the database Secret. The password file below must be a protected local file containing only the database password (without a trailing newline).
    kubectl create namespace tracker
kubectl -n tracker create secret generic tracker-db \
  --from-file=password=/secure/path/tracker-db-password
kubectl -n tracker apply --dry-run=server -f docs/examples/tracker/kubernetes.yaml
kubectl -n tracker apply -f docs/examples/tracker/kubernetes.yaml
kubectl -n tracker rollout status deployment/tracker

    These commands act on the current kubectl context. Check it before applying. The example expects a default dynamic storage class; otherwise specify one on the PVC. Protect/limit Secret access with your cluster's RBAC and secret system.

    Traffic and readiness¶

    flowchart LR
    Browser -->|HTTPS| Ingress
    Ingress --> Service
    Service --> Pod[Tracker runtime pod]
    Pod -->|JDBC| DB[(MySQL)]
    Config[ConfigMap and Secret] --> Pod
    Pod --> Sessions[(Session PVC)]

    Startup/liveness use a TCP check for the JVM listener. Readiness uses /_soad/auth/health, which verifies auth schema/manifest compatibility and may fail during a database outage. Keeping database readiness separate from process liveness avoids restarting the JVM repeatedly for a database failure. See the Kubernetes probe guidance.

    The auth health route is not a complete business-schema diagnostic. Also smoke test the application and inspect logs after rollout.

    Initialize and verify¶

    Create the first administrator on stdin before opening access to the Ingress:

    kubectl -n tracker exec -i deploy/tracker -- soad-auth-admin create-admin \
  --app default --email admin@example.com --name "Tracker Administrator" \
  --password-stdin < /secure/path/initial-admin-password
kubectl -n tracker logs deploy/tracker --tail=100
kubectl -n tracker get pods,pvc,svc,ingress

    The stdin file is a temporary operator secret, not an image input. Check HTTPS sign-in, cookie behavior, project creation, and a private download. Confirm /s0adm/ is unavailable.

    Storage and scaling¶

    The runtime generates model classes inside the application's writable filesystem. This example does not set a read-only root filesystem. It runs as UID/GID 1000 and uses fsGroup for the session volume.

    Jetty's session store is file-based under the JVM temporary directory's s0-session-store. The example persists that path for a single replica. The database also contains revocable application session records; those records alone do not make servlet sessions distributed.

    Do not raise replicas and assume shared login state. Multi-replica operation requires an explicitly designed servlet-session strategy, storage semantics, and testing; sticky routing alone does not provide failover. The example uses Recreate so two versions do not compete for a ReadWriteOnce volume. This introduces deployment downtime.

    Operations¶

    Set CPU/memory requests and limits from measurements; the sample values are a starting point. Monitor readiness, HTTP errors, latency, JVM memory, pool exhaustion, database capacity, and persistent volume usage.

    Back up MySQL and verify restore procedures. Retain application image digests, auth SQL, manifests, and migration history. kubectl rollout undo rolls back the Deployment specification, not database state or a changed ConfigMap. Restore compatible metadata/configuration as part of the same recovery plan.

    The manifest has been supplied as a template; cluster-specific admission, storage, TLS, and database behavior must be verified in your environment.
