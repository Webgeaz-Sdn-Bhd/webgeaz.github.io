    3. Plan a complete application¶

    The tutorial is a project/task tracker for a small team. Begin with the access rules and database model, then build one working slice at a time.

    User stories and access¶

    Members create projects and manage tasks inside projects they own. Each task has a title, a status, and an optional assignee selected from active application users. Assignment is informational: it does not grant access to the project. This keeps the first application's sharing model explicit and small.

    Administrators can delete their own projects, including their tasks and attachments. The projects.delete permission enables the route but does not bypass ownership. Runtime user administration is a separate auth.users.manage permission granted by system_admin.

    Permission admin member
    projects.read yes yes
    projects.write yes yes
    projects.delete yes no
    tasks.read yes yes
    tasks.write yes yes

    The source examples use exactly these codes. Configure them before opening the completed application. Avoid a “catch all” public policy.

    Data model¶

    erDiagram
    SOAD_AUTH_USER ||--o{ PROJECT : owns
    SOAD_AUTH_USER o|--o{ TASK : assigned
    PROJECT ||--o{ TASK : contains
    TASK ||--o| ATTACHMENT : holds
    PROJECT {
        int id PK
        string owner_id FK
        string name
    }
    TASK {
        int id PK
        int project_id FK
        string title
        string status
        string assignee_id FK
    }
    ATTACHMENT {
        int id PK
        int task_id FK
        blob content
        string filename
    }

    Auth tables are generated by the framework. Business tables reference the local user ID but do not store passwords. Attachments are database blobs in this example so deletion and replacement participate in the same database transaction.

    Delivery milestones¶

    1. Configure local auth and confirm sign-in works.
    2. Install the schema, introspect, and create projects.
    3. Add editing, filtering, pagination, and permission checks.
    4. Add tasks, status changes, assignment, and attachments.
    5. Verify cross-user access denial and JSON output.
    6. Package the release, install production auth metadata, and deploy.

    For each milestone keep SQL and source together in version control. Record schema changes as ordered migrations; the CLI does not run them.

    The complete implementation is under examples/tracker. Build it manually with the next chapters or use the full source as a reference. AI is an optional development path described in chapter 11.
