    12. SOAD CLI and local agent workflows¶

    The SOAD CLI lets you use a local editor while synchronizing transactions with an S0ADM server. It does not run the Java server, execute schema migrations, or turn a source sync into a complete production release.

    Install and authenticate¶

    Obtain the CLI from your SØAD distribution. The checked installer targets Webgeaz-Sdn-Bhd releases; older documentation refers to webgeaz/soadcli. Release access could not be verified publicly during this consolidation; use the release/installer supplied with your installation if a repository requires access.

    The installer expects archives named soadcli_<os>_<arch>.tar.gz, containing a soad executable. macOS uses darwin, Linux uses linux, Apple Silicon uses arm64, and x86-64 uses amd64. After downloading and extracting the matching archive, a user-local installation is:

    mkdir -p "$HOME/.local/bin"
install -m 755 /path/to/extracted/soad "$HOME/.local/bin/soad"
export PATH="$HOME/.local/bin:$PATH"

    Add that PATH entry to your shell startup configuration to retain it. The shipped shell installer instead installs into /usr/local/bin using sudo; inspect it before running it. Native Windows packaging is not verified by this guide; use a supported Linux environment such as WSL with the appropriate binary.

    soad version
soad --help
mkdir tracker-workspace
cd tracker-workspace
soad login --server https://ide.example.com
soad list

    Interactive login saves project configuration and credentials in .config.json. Keep it out of Git, release archives, and agent prompts. Use separate project directories for development and production connections. For noninteractive login, the verified CLI supports SOAD_LOGIN and SOAD_PASSWORD, or SOAD_API_KEY and SOAD_APP_ID; inject them from your secret manager instead of command arguments.

    The examples were checked against the installed CLI help (commit 5342396). Use soad COMMAND --help to confirm flags in another version.

    Local and runtime paths¶

    File CLI workspace Runtime under WEB-INF/jython/default
    Controller src/tracker/project/project.py tracker/project.py
    View src/tracker/project/_project/edit.html tracker/_project/edit.html

    Do not copy the extra per-transaction CLI directory directly into runtime routing. The CLI's checksum file tracks local changes, but is not a database migration ledger or a source-control history.

    Daily development¶

    soad create tracker/project
# Edit the scaffolded controller and views in your editor.
soad changed
soad compare tracker/project
soad push tracker/project

    For an existing transaction, pull before starting work:

    soad pull tracker/project

    Preserve any unpushed local edits before pulling. Coordinate with other developers and compare against the current server before pushing; do not assume automatic semantic merging.

    Command Use
    pull --all Download all transactions
    push-all Upload all locally changed transactions
    push tracker/project --zip Alternative upload when a WAF blocks the usual request
    release --version v1.0 --notes "Tracker baseline" Create server source snapshot
    release --list List snapshots
    rollback --version v1.0 Restore a source snapshot
    deploy TARGET_FOLDER Copy source into runtime layout under a target directory
    delete tracker/project Delete remote and local transaction
    clean Delete the local src tree

    Quote wildcard arguments such as 'tracker/*' so the shell does not expand them. Confirm push-remote arguments with its help before using another server. Source rollback does not restore database rows/schema. deploy requires a target folder and does not create auth SQL, install assets, or roll out Kubernetes.

    Use another agent harness with the SOAD skill¶

    The CLI distribution's source bundle includes soad-ai-context/soad-framework/SKILL.md and a reference/ directory. Install the whole folder, not only the main Markdown file. The skill is a guide for writing SØAD code; the soad executable performs synchronization.

    Different harnesses discover skills differently. Use your harness's documented skill-directory/import mechanism, then ask it to load soad-framework for the workspace. If the harness has no skill loader, explicitly give it the main SKILL.md and the referenced files relevant to the task. This does not require the IDE's built-in AI provider.

    Before the first write, ask the agent to confirm:

    • It loaded the skill and recognizes Jython 2.7, generated models, and the CLI layout.
    • It knows the selected development application without printing its credentials.
    • It will create/pull, edit, compare, and push only the transactions in your task.
    • It will keep SQL in migration files for your chosen database execution workflow.
    • It will not treat delete, clean, release, rollback, or deployment as ordinary saves.

    Example request:

    Load the installed soad-framework skill. In this development workspace, pull tracker/task, add a status filter using parameterized queries, preserve ACCESS_POLICY and ownership checks, show the diff, then push the approved change. Do not modify schema or publish a release.

    Older skill bundles may contain obsolete authentication or rendering examples. Use this repository's contracts when they disagree, and update the bundle. After pushing, test the real application session and expected response content; an IDE API token does not authenticate a browser to the runtime application.
