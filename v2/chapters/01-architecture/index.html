    1. Introduction and architecture¶

    SØAD maps HTTP requests to small Jython classes called transactions. A transaction loads or changes database models and chooses a response: an HTML view, JSON, a download, or a redirect. Here, “transaction” names the controller; the database transaction around a request is a separate concept.

    The components¶

    Component Responsibility
    Java engine Embedded Jetty server, configuration, JDBC pools, model generation, request context
    Jython runtime Transaction dispatch, rendering, authentication, filters, file uploads
    Application Your transactions, templates, public assets, schema, and security manifest
    S0ADM Browser development tools, application configuration, AI, and release preparation
    SOAD CLI Synchronize transaction source/views between a local workspace and S0ADM 
    flowchart LR
    Developer --> IDE[S0ADM development server]
    Developer --> CLI[Local editor and SOAD CLI]
    CLI --> IDE
    IDE --> Release[Application release]
    Release --> Runtime[Application runtime]
    Browser --> Runtime
    Runtime --> DB[(Application database)]

    The deployed runtime uses its own database accounts and application identities. It does not need the IDE database or an IDE session.

    Request lifecycle¶

    sequenceDiagram
    participant B as Browser
    participant F as Transaction filters
    participant T as Transaction engine
    participant A as Application auth
    participant C as Controller
    participant D as Database
    B->>F: HTTP request
    F->>T: Continue
    T->>D: Open request database transaction
    T->>A: Authorize action
    A-->>T: Identity and access decision
    T->>C: Invoke allowed action
    C->>D: Query or update models
    C-->>T: Renderer or redirect
    T->>D: Commit on success, rollback on exception
    T-->>B: Response

    Authorization failure prevents the controller action from running. Rendering is also part of request processing. External email/API calls and filesystem writes are not undone by a database rollback.

    Application layout¶

    webapp/
  assets/tracker/                  public CSS and other static assets
  WEB-INF/
    jython/default/
      __init__.py
      tracker/
        __init__.py
        project.py                class Project
        _project/
          project.html
    security/app-security.json
    deploy/auth-mysql.sql
    deploy/auth-h2.sql
    classes/models/               generated; do not author or commit

    /t/tracker/project invokes Project.view(ctx). /t/tracker/project/save invokes Project.save(ctx). The CLI uses an additional per-transaction directory locally; see the mapping.

    Language and database boundaries¶

    Transactions run on Jython 2.7, not Python 3. Use "%s" % value instead of f-strings. Java imports work directly; CPython binary packages and pip install are not an application dependency mechanism. Put reviewed Java dependencies in the application's runtime library directory and restart.

    ActiveJDBC models are generated from the live schema. Define tables first, then introspect or restart before importing new models. Business datasource support and built-in authentication support differ: the shipped local-auth SQL generator supports MySQL and H2, not every JDBC database.
